# ThreadPort 战略与技术评估

**核心判断：值得进行一次有明确退出条件的全职验证，但目前的证据不足以支持直接扩张成平台公司。** 最值得验证的产品是：让正在进行的编码任务在更换 Agent、会话或执行环境后可靠接续，并明确指出哪些状态已经过期、哪些结论没有证据。开源协议可以成为这一产品的结果；在实际采用之前，它仍是一个项目自定义格式。

评估对象为 Frankie-Xu/threadport，代码快照固定于 `31ae6771bbb135bcf690e713c02869136db4b3ca`，公开数据检索于新加坡时间 2026 年 9 月 14 日。创业假设为创始人全职投入、先通过开源获得用户，再验证团队付费。下文将公开事实、可复现代码观察、分析判断和待验证假设分开；所有增长门槛与价格均为建议实验参数，不是行业均值或收入预测。

## 1. 投资时间之前的三个判断

第一，**广义市场已经存在，狭义需求仍未验证**。跨会话记忆、编码任务状态和 Agent 工作记录已经出现高关注度开源项目，但这不能证明频繁切换 Agent 的人足够多，更不能证明他们愿意为迁移单独付费。ThreadPort 需要验证的是“每周反复发生的接续失败”，而不是让受访者承认“上下文很重要”。

第二，**现有实现是有工程基础的早期原型，尚未形成可靠的接续闭环**。结构化 Capsule、四类日志适配器、JSON/Markdown 导出、Git 摘要和脱敏已经存在；会话发现、真实目的端接续、工作区一致性验证和用户留存仍缺少证据。现有测试全通过与这些缺口可以同时成立。[1][2]

第三，**竞争比小型 handoff 项目的数量所显示的更激烈**。Entire 已覆盖 Git 关联会话记录与接续，并有显著资金和渠道优势；Claude-Mem 已扩展到多 Agent；VS Code 文档已经直接描述 Claude、Codex、Copilot 之间的 session handoff。仅仅主张“跨 Agent”或“Git + 上下文”，不足以形成独占位置。[8][9][10]

建议的次序是：先做两款 Agent 之间可靠、可测量的接续，再验证团队协作价值，最后决定是否扩大协议和托管服务。现在同时做十种适配器、通用记忆库、编排平台、企业审计和知识图谱，会把创始人的注意力消耗在尚未确认的需求上。

开发顺序总体合理：先定义结构与校验，再做日志适配与导出，随后补安全写入、路径隐私、JSON handoff 和适配器共享组装。最新 #24 减少了 Claude/Codex 的重复组装逻辑，但行为仍需要跨适配器回归。密集的小 PR 证明能推进实现，不能证明代码经过独立评审或在真实用户环境中成立。

当前 README 的入口偏向贡献者：`npm ci`、`npm run check`、传入日志文件路径。普通使用者需要的是“自动找到这次任务，交给另一个 Agent”。`handoff` 目前写出 Markdown 或 JSON 文件，尚未形成目的端确认接收与继续执行的闭环。`targets` 主要通过 `which` 判断命令存在；命令存在不代表已认证、版本兼容或支持正确的接续方式。[4]

## 3. 代码检查：先兑现 portable 与 verifiable

本节所述复现使用人工构造日志和临时 Git 仓库，没有调用真实第三方 Agent。复现脚本与结果随报告交付。它们验证实现边界，不代表测量了真实使用中的发生率。

### 3.1 文件路径会丢失层级

在默认 portable 模式下，两个仓库内绝对路径 `src/a/index.ts` 和 `src/b/index.ts` 均被输出为 `index.ts`。`portablePath()` 中对 `resolve(rel)` 的绝对路径判断使 POSIX 上的相对路径返回分支失效，随后退化为 basename。结果是目标 Agent 无法区分两个文件，证据定位也会失真。[5]

**优先级：P0。** 应按声明的 source root 转换仓库内相对路径，保留子目录；仓库外路径使用显式 opaque locator。测试至少覆盖同名文件、空格、Unicode、Windows 分隔符、worktree 与跨机器 root 映射。隐藏用户名与保留文件身份必须同时满足。

### 3.2 失败—成功—再次失败，被折叠成“已解决”

输入相同 `npm test` 的退出码序列 `1 → 0 → 1`，`collapseFailures()` 仍把失败标为已解决。实现只检查第一次失败之后是否有成功，并通过 `seen` 跳过后续同命令失败。复现里 `tests` 保留最后一次失败，而 `failures` 显示 resolved，整体状态为 active。[5]

**优先级：P0。** 保存每一次执行，并按最新执行和对应代码状态计算“当前结论”。测试通过必须绑定当时的文件/Git 摘要；在之后有相关改动时，至少标记 stale。一次历史成功不能覆盖之后的失败。

### 3.3 格式校验不等于状态验证

`validate` 调用 JSON 解析和 schema 校验后直接输出 `valid`，并不读取当前工作区。将一个格式合法的 Capsule 放入已经变化的工作区，依然返回成功；这是当前命令的实际语义，不能宣传为“工作状态已验证”。[4]

`gitStateMatches()` 又要求 root 字符串相同，而 portable Capsule 使用 `.`，`readGitState()` 返回绝对路径。复现中在任何文件变化前立即比较也得到 false。它缺少跨位置身份映射；当前 CLI 也没有把该比较接入验证流程。[6]

**优先级：P0。** 明确区分 `validate-schema` 与 `verify-workspace`。后者应输出 matched、drifted、unverifiable 及原因，比较 repository identity、base commit、相关文件摘要和工作区映射。整仓 dirty hash 可以检测变化，但不能判断变化是否影响当前任务。

### 3.4 提取规则会保留旧目标、漏掉约束

复现中用户先要求 A，再要求改为 B，最终 objective 仍是第一条消息的 A。中文“不要修改数据库”没有进入 constraints；英文意图句 “I will use SQLite” 则直接成为 decision。`pnpm test` 未被现有测试命令正则识别。[5]

**优先级：P1，公开承诺之前解决。** 记录目标修订、决策提出者、采纳状态和来源事件。把 observed、user-confirmed、derived、unknown 分开，不要制造未经校准的 `confidence: 0.92`。确定性代码适合提取客观事件；语义总结可以作为可选层，但输出须带引用和人工编辑入口。

### 3.5 会话记录与当前 Git 快照可能来自不同时间

组装 Capsule 时读取的是提取当下的 Git 状态。旧日志可以与今天的工作树一起打包，当前实现未建立“日志最后一次测试发生于哪个代码状态”的完整联系。这样得到的 dirty hash 只能证明提取时看到的工作树，不能追溯证明日志中的测试对今天的代码有效。[5][6]

**优先级：P1。** 分开 source-event time、capture time、verification time；没有历史快照时明确标为不可验证，绝不补造测试 provenance。无需一开始实现通用执行重放。

### 3.6 安全与发布语义需要收窄

本地处理、不自动执行命令、排除指定隐藏推理字段和常见密钥脱敏，是合理默认。但 JSON 中的 `execute_commands: false` 及 Markdown 中的确认提示本身没有执行强制力。接收方 runtime 才能限制文件写入与命令运行；签名也只能帮助验证完整性/来源，不能证明摘要正确或命令安全。[4][7]

此外，“read-only”应解释为不修改源项目代码、不执行源命令，产品仍会写出 Capsule 文件。发布前应列清哪些路径会写入、哪些内容会发送给目的端模型。默认本地保存不能推出“导入云端 Agent 后也不离开机器”。

**整体判断：基础设计有价值，核心语义尚未可靠。** 先修复上述问题，比继续扩大 adapter 数量更能支撑项目信誉。现有四款适配器的主要测试各基于一个 synthetic fixture；应公开支持级别为“已实现解析”，再以经授权脱敏的真实日志、官方 hook 输出和真实接续实验逐步提高兼容声明。[2]

## 4. 技术与市场趋势

### 4.1 Agent 使用增长是顺风，但不能代替切换需求证据

JetBrains 2026 年 8 月报告基于超过 15,000 名职业开发者，披露 2026 年 5–7 月 Claude Code 使用比例约 39%、Codex 16%、OpenCode 7%；报告也描述 Agent 高频进入工作流。该来源有区域配额和加权方法，但仍属厂商调查。各工具占比不能相加得出多工具用户比例，未测到的“每周跨工具切换率”必须自行验证。[11]

Stack Overflow 2025 调查显示，84% 为“使用或计划使用 AI”，职业开发者每天使用比例为 51%；46% 不信任准确性，而信任者为 33%。该调查中仅 17% 的 Agent 用户认同其改善了团队协作。它是历史基线，定义与 2026 年 JetBrains 调查不同，不能拼接成严格增长序列。[12]

这支持两个需求假设：个人需要减少重复解释，团队需要可信的工作交接。但“AI 很流行”既不能推出交接频次，也不能推出团队预算。

### 4.2 原生产品已经解决一部分问题

Claude Code 有 CLAUDE.md 和 auto memory，后者记录纠正与偏好；其文档将自动记忆描述为机器本地、同仓库 worktree 共享。单平台连续使用者已有低摩擦替代品。[13]

VS Code 文档明确支持通过 session target 把历史与上下文交给不同 harness，包括 Claude、Codex 和 Cloud。它不是未来猜测，而是当前文档已描述的能力。ThreadPort 若只是在一个已有统一工作台里换模型，很难要求用户再安装工具。[10]

因此应寻找平台没有替用户完整处理的边界：跨独立 CLI、不同 workspace、不同人，以及接续时判断状态过期。具体支持仍须通过版本化实测，不能笼统宣布“所有平台做不到”。

### 4.3 更大上下文降低搬运价值，增加筛选价值

这是技术机制上的推断：如果模型能便宜地重新读完整仓库，压缩文本和摘要本身的价值会下降；但代码无法说明被撤销的决策、未完成的业务要求和测试发生时的状态。应衡量“恢复正确工作的成本”，同时统计 Token、延迟、重扫文件与错误行动，不要只宣传上下文缩小百分比。

真正有价值的上下文是与当前任务相关、仍有效、可追溯的最小集合。全量记录与多写总结都可能让下一个 Agent 更困惑。

### 4.4 互操作标准应作为接口利用

| 标准/约定 | 主要解决的问题 | ThreadPort 应承接的部分 |
|---|---|---|
| AGENTS.md | 面向 Agent 的项目说明与规则 | 保存短入口，指向任务状态；不反复把所有日志塞进去 |
| MCP | 模型应用访问工具与数据 | 暴露只读查询和显式接续准备工具 |
| ACP | 编辑器与编码 Agent 的通信 | 条件成熟时作为目的端/来源端集成接口 |
| A2A | 独立 Agent 之间的协作通信 | Capsule 可作为任务 artifact；无需重建通信协议 |

这些标准解决不同层次的问题，并不自动统一所有厂商的私有日志或证明任务状态真实。ThreadPort 的候选价值在内容语义、有效性和接续体验，而不是再命名一个传输协议。[14][15][16][17]

### 5.1 小竞品多、大采用少：既是机会，也是警告

同一种需求被独立重复开发，说明问题容易被感知；但若工具长期停留在低采用，可能是分发不足、痛点低频、安装成本过高，或者一个 Markdown 文件已经够用。仅凭仓库数无法区分这些原因。rosehgal/handoff 的 API `pushed_at` 仍停在 2026-06-30，也提醒不能把完整 README 当作持续运营证据。[18]

验证方法是直接观察最近一次切换：多久发生一次、实际丢失了什么、现在用什么补救、是否愿意让 ThreadPort 进入下一次工作。只有行为数据才能判断这是“没有强者占领的空间”，还是“很多人做过但留不住用户”。

### 5.2 强竞品证明预算方向，同时压缩你的选择

Entire 2026 年 2 月官方公告称获得 6,000 万美元种子融资，创始人为前 GitHub CEO Thomas Dohmke。该事实说明资金和渠道竞争客观存在，不证明它已经盈利或拥有产品市场匹配。其 Git 上下文、traceability 与 handoff 方向和 ThreadPort 的长期愿景高度重合。[24]

因此不推荐以“再做一个 Entire”竞争。更可行的假设是：以不要求用户迁入另一套存储/平台的可携带任务包为入口，兼容既有 session、Git 和记忆系统；以接续时的有效性检查与明确缺失清单建立使用理由。这是待验证差异，不是已经存在的护城河。

竞争者的 issue 可以帮助选择测试：Claude-Mem 有用户要求减少 observer 调用带来的 token 消耗；Entire 有非 ASCII 文件名导致 checkpoint 关联问题的报告。它们提示低额外成本、跨平台正确性值得投入，但单个 issue 不能估算问题普遍性，竞品修复一个 bug 也可能消除短期优势。[25][26]

### 5.3 能合作的竞争，比完全避开竞争更有利

候选合作方式：从 cass 发现历史，从 Entire 读取已有记录，用 Beads issue ID 绑定任务，向不同 Agent 输出经过验证的当前状态。先选择一个能带来真实使用者的集成，而不是同时做全套。

合作是否成立，要看对方用户是否反复使用、维护者是否接受接口，以及双方是否避免重复保存全部敏感数据。一个 README 链接或一次 PR 合并只证明连接存在，不证明形成生态网络效应。

### 5.4 名称已经有传播冲突

`megarampo/threadport` 与 Chrome Web Store 上另一款名为 Threadport 的 AI 对话迁移产品均已存在；商店产品描述甚至包含把浏览器对话转成 capsule、交给 IDE/MCP 的相近概念。这些不是 Frankie-Xu/threadport 的用户或成绩。[27]

品牌混淆会影响搜索、口碑归属与媒体理解。建议在首次大规模发布之前完成名称可用性核查，或明确使用独特品牌加 “coding task handoff” 描述。本报告不做商标法律判断，也不认为已有同名就必然需要放弃项目。

## 6. 应选择的客户与核心场景

推荐首个用户画像：**5–30 人的 AI 重度开发团队中，经常在两个独立 Agent 之间切换、同时维护多个 branch/worktree 的工程师或技术负责人。** 团队规模是招募范围假设，不是已知付费群体。

首个场景：Claude Code 完成部分改动后，开发者希望用 Codex 继续实现或复核；工具应给出当前目标、仍有效的约束、已改文件、最后测试状态、阻塞项和接续动作。必须同时支持同 Agent 的下一次 session，否则只有跨品牌切换才触发使用，频率可能太低。

| 人群 | 使用动机 | 潜在频率 | 付费可能性假设 | 优先级 |
|---|---|---|---|---|
| 多 Agent 重度个人开发者 | 额度、能力差异、主动交叉复核 | 中到高，需实测 | 偏低到中 | 最先验证产品 |
| AI 原生小团队 | 同事接手、PR 审查、跨机器任务延续 | 中到高，需实测 | 中到高 | 最先验证买单 |
| 服务商/开发外包团队 | 多客户任务、交付说明与接手 | 中 | 中；重视隔离 | 第二批访谈 |
| 大企业平台/安全团队 | 留存、权限、审计政策 | 潜在高 | 高客单但长周期 | 暂不主攻 |
| 浏览器聊天用户 | ChatGPT/Claude 对话搬运 | 多为偶发 | 低到中 | 暂缓 |

必须击败的最低成本替代品是：让源 Agent 写一份简短 `HANDOFF.md`，新 Agent 阅读它与 `git diff`。如果做不到可靠性或恢复成本的明显提升，再精巧的 schema 也不足以推动安装。

## 7. 产品方向取舍

下表为基于本次证据的相对判断，不使用伪精确评分。

| 方向 | 分发/增长潜力 | 创业付费潜力 | 当前竞争压力 | 决策 |
|---|---|---|---|---|
| 通用聊天迁移 | 场景直观，容易演示 | 偏弱且可能低频 | 已有同名及多款扩展 | 暂缓 |
| 原生 session 格式互转 | 很适合演示与搜索获客 | 单独收费较难 | ctxmv + 平台原生功能 | 作为入口，不押注全量格式转换 |
| 通用长期记忆 | 高关注度已经被证明 | 存在商业路径 | 很高，成熟项目多 | 不全面进入 |
| 可验证任务接续 | 场景具体，需证明效果 | 可连接团队协作预算 | 高，但仍可做窄场景优势 | 当前主线 |
| 企业审计平台 | 开源传播较慢 | 潜在高客单 | Entire 等直接进入 | 先验证两个付费流程 |
| 独立开放协议 | 采用后有生态杠杆 | 间接、难单卖规范 | 现有约定与平台接口 | 从真实集成中提炼 |

产品承诺建议为：“换一个 Agent，继续同一项工作；目标、改动和测试状态都能追溯。” 演示中展示换工具后保留了什么、发现了什么过期状态；不要承诺“无损恢复所有理解”。

技术主张可以保留 portable、local-first、verifiable，但把 verifiable 解释成具体证据层级：格式是否合法、仓库是否匹配、相关文件是否变化、测试记录属于何时、哪些语义由人确认。不同层级不能合并成一个绿色勾。

## 8. 产品结构与护城河

建议的数据流为：来源事件 → 标准事件记录 → 当前任务状态 → 有效性检查 → 接续包 → 目的端接收回执。这里的回执是“目的端成功读到并识别状态”，不是未经观察就声称任务已经正确继续。

最小状态必须包含稳定 task ID、来源 Agent/version、源事件定位、当前目标与修订、用户确认的约束、文件相对路径、最近测试及执行时状态、未解问题，以及无法验证项。增加 predecessor/supersedes 关系，让 Capsule 是可演进的状态，而不是同名覆盖的一份摘要。

对外使用渐进式上下文：先给短 resume brief，再按需要读取文件证据和历史事件。客观事实抽取可保持确定性、无额外模型调用；可选语义压缩必须单独标记成本、来源和不确定性。这样才有机会兼顾轻量与正确性，而不把“本地/零调用”变成无法准确总结的自我限制。

**真正可能积累的资产有四项。** 第一，经授权、可公开复现的异构会话与故障样本；第二，被真实使用的跨工具接续接口；第三，持续更新的版本兼容与质量报告；第四，团队已经信赖的接续和审查流程。它们都需要时间和采用来建立。

Adapter 数量本身更可能是维护负债。Schema、MCP 包装、开源许可证、哈希或签名也都容易复制。只有当外部项目依赖你的语义、兼容测试和交接质量时，维护工作才可能转化为进入壁垒。避免靠私有格式锁住用户；将收入建立在协作、运维和治理便利上。

## 9. 90 天全职路线

以下门槛用于决定是否继续投入，样本较小时只能作方向信号，不是统计意义上的 PMF 认证。

### 第 1–14 天：纠正核心语义，同时接触需求

工程侧：修复路径折叠、失败状态折叠和 portable Git 比较；清楚区分 schema validation 与 workspace verification；补目标变更、未知事件与语言覆盖。发布可复现安装包，使 README 所写命令与当前稳定版一致。

需求侧：完成约 20 次合格访谈，其中至少 10 次观察最近真实任务的切换或恢复。记录工具组合、次数、当前补救、损失类型和成本，避免只问“你会不会用”。先招募 5 个愿意连续试用的团队/个人，不把亲友点赞算作验证。

退出条件：如果找不到反复发生的接续痛点，或绝大多数人一份 Markdown 已足够，应收窄为维护良好的工具，不直接开建团队平台。

### 第 15–30 天：完成一个双向闭环

主攻 Claude Code ↔ Codex，两端只承诺明确测试过的版本。实现会话发现、捕获、校验、目的端加载和反馈；手动控制先可靠，再加入必要 hook。目的端的具体启动参数必须逐版本核查，不能假定各 CLI 有统一 `--prompt-file`。

产品目标：陌生使用者在 5 分钟内完成首个接续，不要求寻找日志路径；一般接续准备延迟单独记录，并纳入基准。完成至少 30 个可评分任务实验及首批约 20 名真实试用者。若只完成文件导出，仍不能计为激活。

### 第 31–60 天：看重复使用，而非只看发布热度

目标是观察至少 50 名激活用户的行为；其中 20 名在四周观察期内于至少三周完成真实任务接续，可作为早期积极信号。记录同工具恢复与跨工具切换的占比。如果 80% 以上价值来自同工具恢复，则将市场定位调整为任务连续性，而不坚持跨品牌叙事。

工程投入以真实失败为主：版本变化、worktree、中文路径、历史日志与当前工作树漂移。只按真实需求增加第三种 Agent。MCP 若显著简化试用者的使用路径再做；它不是通往 10k stars 的必需徽章。

### 第 61–90 天：验证买单与生态入口

从留存最好的团队中提出付费试点，测试共享任务包、PR 接续说明与集中管理中的一个流程。目标为约 5 个付费试点、其中至少 3 个进入第二个付费周期；销售周期跨出 90 天时，以可验证付款和明确采购进度记录，不把口头兴趣算收入。

并行争取 2 个第三方真实集成，至少一个能产生重复使用。仅在这些接口被使用后整理稳定规范与兼容套件。若留存好但没人愿付费，可选择开源影响力路径或调整买方；若留存和付费都弱，应停止扩大基础设施范围。

全职时间建议：45% 产品可靠性与体验、30% 用户观察和跟进、15% 文档/演示/分发、10% 竞品与生态。此比例是起点，可按最大瓶颈调整。融资、招聘和全面重写技术栈都不应成为当前验证的前置条件。

## 10. 基准：证明比手写交接更好

基准必须比较完成同一任务的结果，而不是仅比较 Capsule 大小。第一阶段用 30 个任务探索明显故障，之后扩展至 100 个以上、多仓库、多语言任务；保留训练/开发用例与最终评估用例的区分。

比较组建议包括：新 Agent 只读仓库；源 Agent 生成 HANDOFF.md；原生 resume/compaction（适用同 Agent 场景）；ctxmv（支持的迁移方向）；ThreadPort。Entire/Claude-Mem 在准备条件一致的场景下追加比较，不强行把长期记忆和一次性导出混在同一赛道。

任务覆盖：中途改需求、否决方案、失败后回归、未提交文件、分支变更、旧测试、多语言路径、工具输出缺失和恢复后再次修改。预先保存金标准目标、约束与测试状态。允许 unknown 正确表达缺失，不能用编造字段提高所谓覆盖率。

| 指标 | 定义 | 原因 |
|---|---|---|
| 任务接续成功率 | 在限定时间内达到预设验收的任务数 / 尝试数 | 主要结果指标 |
| 首个正确动作时间 | 目的端启动到第一次符合验收路径的有效动作 | 衡量恢复成本 |
| 关键约束遗漏 | 丢失必须遵守要求的任务占比 | 比摘要流畅更重要 |
| 错误确定性 | 将失败/未知/过期声明为通过或有效的比例 | 衡量误导风险 |
| 重复工作 | 重做已完成操作、重复无效尝试次数 | 衡量工作状态保留 |
| 总资源成本 | 提取、摘要、读取、执行总 token、费用和时长 | 防止把成本移到上游 |
| 安装与接入成功 | 能独立完成完整流程的用户比例 | 影响增长转化 |

同一目的端模型版本、同一预算和相同仓库起点，随机化条件，重复运行；同时报告样本数、分布和失败案例。30% 恢复时间改善可作为内部目标，但在有结果之前不能写成宣传事实。用真实成功率选择架构，比提前建立庞大协议更有价值。

## 11. 10k stars：将目标拆成增长机制

现有数据不支持“12–18 个月一定达到 10k”或一个可信成功概率。一个两天的仓库没有足够时间序列，其他项目的 stars 也受到创始人影响力、受众规模和发布事件影响。10k 应作为分发目标，并与使用和付费指标分开。

### 11.1 三条需要分别建立的路径

第一条是**搜索获客**：围绕具体任务创建文档与演示，例如 “continue Claude Code task in Codex”“resume agent work after context reset”“handoff with dirty worktree”。每篇内容都应能复现一个结果，包含失败边界和版本信息。

第二条是**使用带来的协作分发**：用户把任务包交给同事或放入 PR，同事通过可读报告了解并尝试 ThreadPort。默认支持纯 Markdown 阅读，接收方不必安装才能查看；需要验证或继续工作时才安装。公开分享必须显式选择并预览脱敏内容。

第三条是**生态分发**：以可靠适配器、失败基准和清晰 API 被工具作者引用。第三方集成产生实际调用才算成功；目录收录和 badges 只是入口。

### 11.2 有门槛的开源阶段

| 阶段 | 产品/采用条件 | 合适的传播动作 |
|---|---|---|
| 0→100 | 两款 Agent 完整闭环；10 位陌生用户独立用成功 | 60–90 秒真实演示，定向发布到相关社区 |
| 100→1,000 | 留存开始出现；基准可复现；稳定安装与支持矩阵 | Show HN、技术文章、带数据的对比和真实案例 |
| 1,000→3,000 | 外部贡献、第三方集成、团队案例 | 联合集成发布、维护者合作、教程与故障语料 |
| 3,000→10,000 | 使用场景被社区重复推荐；维护与版本质量稳定 | 让接续报告、兼容套件和生态成为持续入口 |

这些是顺序性条件，并非星数保证。针对开发者的英文文档和演示应优先完整，再提供中文资料。不要购买 stars、刷榜或用无关功能制造发布次数。

### 11.3 用算式看分发规模，不伪造转换率

假设每位合格仓库访客的 star 转换概率分别为 2%、5%、10%，达到 10,000 个 stars 所需累计合格访客约为 500,000、200,000、100,000。这里只做敏感性分析，转换率未被本项目测量，而且长期独立访客去重很难准确。

这个量级说明仅靠一个 launch 通常不应成为计划的全部。需要持续搜索入口、重复引用和集成分发。记录 GitHub traffic 的可见窗口，避免跨周把 unique visitors 当作永不重复的用户累加。公开 stars 属于传播指标，不能作为市场规模估计。

## 12. 商业化：卖协作结果，保留本地核心

建议长期免费开放本地捕获、schema、导出、验证、两端接续与基础适配器。这些功能既是获取开发者的理由，也是对数据可携带性的承诺。对简单本地迁移收费可能迫使用户回到 Markdown。

优先验证的付费价值是团队共享与权限、跨设备安全同步、PR 关联与接手说明、统一留存/删除、集中兼容支持。企业 SSO、私有部署和审计导出在有采购需求后再做；不把未验证的哈希摘要包装成合规保证。

可测试两种报价：个人增强功能每月 15–25 美元，或小团队试点每月 200–500 美元。价格是假设，用带期限、具体交付和退出方式的试点验证。衡量试点使用、复购和节省的工程时间，而不仅是签订意向书。

商业量级的示例：20 个团队 × 10 席位 × 20 美元/月 = 4,000 美元 MRR，年化 48,000 美元，未扣托管、模型、支持和获客成本；200 个团队 × 500 美元/月 × 12 = 120 万美元年化经常性收入。它们只是算术情景，不是 TAM/SAM/SOM 或可实现预测。

关键缺失是可触达团队数、真实购买率、留存、支持工时和扩张率。靠一次手工代办收费可以验证痛点，但不能直接证明可重复 SaaS 收入。若以创投型公司为目标，还须证明产品能从单人便利扩展到团队关键流程；若只有个人付费工具，也可能成为可持续业务，只是资本和增长路线不同。

## 13. 用什么证据继续，什么证据转向

| 观察到的情况 | 更合理的解释 | 下一步 |
|---|---|---|
| Stars 增长、安装少 | 演示吸引人，落地路径或受众不匹配 | 优先首次使用漏斗 |
| 安装多、接续成功少 | 可靠性/兼容性没有兑现 | 停止扩大宣传，修当前两端 |
| 成功一次、之后不再用 | 需求低频或手工替代足够 | 测同 Agent 次日恢复与团队交接 |
| 个人留存高、团队不付费 | 效率工具成立，买方价值不足 | 调整付费包或接受工具业务 |
| 团队试点愿付费但持续靠人工 | 痛点存在，产品交付成本过高 | 自动化共同流程，限制定制 |
| 被强竞品加入同功能 | 功能差异快速缩小 | 用兼容、接续质量、可携带性证明理由；否则整合 |
| 纯 Markdown 达到同等结果 | 额外系统无足够增益 | 收窄为 skill/测试套件，不强建平台 |

没有竞争对手的方向应提高验证要求；已有大竞品的方向则提高差异化和分发要求。优先寻找的是“需求已被证明，但特定工作流仍被现有产品处理得不够好”的空间。这里的潜在空间是低摩擦、跨环境、能识别过期证据的任务接续，是否成立仍需要 90 天验证。

## 14. 创始人本周的优先顺序

1. 修复并公开验证 portable 路径、最新失败状态、schema/工作区验证三类问题。
2. 完成稳定安装，发布说明准确区分 main 与 v0.1.0；同步检查品牌混淆。
3. 只针对 Claude Code ↔ Codex 做一次真正接续，录下完整过程和失败边界。
4. 招募第一批高频用户，观察真实工作；在决定追加适配器之前收集行为。
5. 建立 HANDOFF.md 对照组，开始测接续成功率和总恢复成本。
6. 从第一天分别记录开源传播、重复使用、团队购买三类证据。

当前最值得投入的方向是可靠任务接续。只有当它反复替用户避免重做和错误接手，协议、生态和商业化才有坚实基础。
