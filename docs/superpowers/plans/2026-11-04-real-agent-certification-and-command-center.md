- 每次派发一个工作包，实施会话先核对最新 main、未提交变更、依赖与文件范围。阶段 0 沿用原修复会话，新功能继续在项目内独立会话实施。

## 5. 阶段 1：真实 Agent 接续认证

### 5.1 认证单位与证据边界

一条认证记录绑定候选源码 SHA、已安装 tarball SHA-256、OS/架构、Node 版本、源/目标 Agent 版本、接续模式和任务场景。只改文档可追加证据提交；运行时代码、runner 或包内容变化后，原记录不能直接迁移为新候选通过。

先用自动回归尽早暴露问题，再冻结候选做实机矩阵。实测发现产品问题时退回相应包修复、重新冻结候选；最终 G1 的 24 格必须对应同一运行时候选。阶段 2 改动接续、来源身份、授权或存储路径时，先做影响分析并重跑相关真实路径，阶段出口再对最终安装包完成所声明支持范围的矩阵。纯文档和测试文件变化单独记录，不能冒称旧运行时证据来自新安装包。

区分三类结果：接口探测、合成集成、真实功能认证。现有 `nativeResume`、`newSessionWithContext` 布尔值表示接口匹配，不自动表示实机认证。增加认证展示时采用独立、可追溯的元数据，不悄悄改写旧字段含义。

真实功能成功也不自动产生 `received/confirmed` 或 `verified-complete` receipt。只有达到相应存储证明边界的受信任本地验证器才能写入 attestations。目标 Agent 声称收到、输出某个标记、退出 0 或真实测试任务通过，都不能替代该权限边界。

### 5.4 异常与恢复矩阵

| 场景 | 必须观察到的行为 |
| --- | --- |
| 未安装、版本未知、help 变化、不支持的包装程序 | 清楚说明能力缺口并支持导出；不拼接 shell 作为兜底 |
| 未登录、认证失败、服务不可达 | 来源任务和预览保留，登录由目标处理；不记录虚构成功或把认证错误当作任务完成 |
| 用户拒绝、非 TTY、`--yes`、重复消费 | 拒绝后执行次数为 0；已消费包不会再次启动 |
| 审阅后程序、版本、argv、目录、文本、任务 revision 或工作区变化 | 批准失效，要求重新准备/审阅；不能沿用旧计划 |
| 原生会话缺失或身份不符 | 明确报错；不能静默换成另一个会话或丢掉当前人工上下文 |
| 两个包争抢同一工作树 | 同一 dataDir 内至多一个执行者；冲突方保留可恢复状态。多个 dataDir 的现有限制写明 |
| 目标非零退出、用户中断、观察者崩溃/重启 | 失败、中断、unknown 分别记录；身份不明时不自动释放工作区或再次启动 |
| 上下文含中文、引号、换行、`$()`、反引号、长文本 | 实际传输遵守冻结方案，无 shell 副作用；超容量明确拒绝，人工约束不静默截断 |
| 脱敏改写了下一步命令或绝对路径 | 保留审阅提示和必要阻断，用户明确改成可执行的可移植写法后重建 |
| 导入伪造 runtime/user 来源、receipt、attestation ID 或责任事件 | 信任不升级；错误目标、摘要、阶段、nonce、过期证明和重复 ID 的回归保持通过 |

合成测试负责精确覆盖参数和竞争窗口。登录、实际上下文传输、原生恢复、真实中断和恢复等只能由实机证明的分支，分别在适用平台执行。每格设置显式时间/费用预算；超时停止后续调度并记录已知状态，不把超时解释为进程已停止。

### 5.5 单格证据与 G1

每格最少保存以下匿名元数据及判定结果。

- 候选源码与包摘要、平台/架构/Node、源/目标 Agent 精确版本、场景 ID、运行时间、最终状态。
- handoff/launch plan 的摘要关联、模式、工作区身份匹配结果、源/目标 session 关系检查结果。真实 session ID 与私人路径留在本地证据区。
- 人工目标/约束对应的检查项、允许产物与受保护文件摘要、独立测试命令及结果、目标进程结果、出现过的警告与首次失败。
- 实际启动参数与预览一致的检查。目标原生记录可提供完整可见输入时，另核对传入文本；缺少该层观测时明确 unknown，不用目标自报代替接收证明。
- 使用的环境观测范围。缺少环境信息继续标未知，不能由代码指纹相同推导当前测试认证。

**G1 验收**：当前候选 24 格功能判定全部通过；异常矩阵的适用分支有证据；没有未解决的高优先级安全或错误成功问题；本窗口独立复审通过；最终代码的完整自动验证与三平台 CI 成功。`not_run`、环境受阻或 `observed_with_issue` 均不能计作通过。

此门槛证明指定版本的功能接续，不证明目标理解全部约束、任意任务正确、完整环境一致或 receipt 已被受信任确认。Windows 与其他 Agent 版本按各自证据单独声明。

## 6. 阶段 2：多会话指挥台

### 6.1 MVP 场景与数据语义

复现本项目实际使用方式：一个会话负责修复，另一个负责审查。修复方给出新版本后，审查方请求修改；修正形成新版本，重新复审；指挥台始终展示当前责任、待审版本和下一步。GitHub CI 的实时读取留给阶段 7，本阶段只显示已有本地证据，不能编造远端检查结果。

首页每个任务提供以下信息，详情复用已有证据、manifest 与 receipt。

| 信息 | MVP 语义 |
| --- | --- |
| 责任方 | 当前 scope 的已确认执行者、审查者和下一责任方；提议、未知与冲突单独显示 |
| 会话与运行 | 分开标识 task、session、run；同一 session 的不同 run 不相互覆盖，缺 run ID 不猜测补全 |
| 最后观察 | 动作、来源、可用时间、证据级别和证据入口；来源自报不能变成经过验证的动作 |
| 交接状态 | manifest 对应的目标、receipt 阶段/状态、过期与缺口；不把 receipt 的后期阶段直接画成任务完成 |
| 审查结论 | 对明确交付对象的待审、请求修改、批准、撤回或已失效；保留历史，结论不跨版本继承 |
| 建议下一步 | 查看证据、确认分工、修改后复审、重新准备或打开终端接续；动作来自固定应用流程 |

任务生命周期继续由用户控制。角色是本地任务分工，不是团队账号权限。子会话出现、标题相似、共享目录、Agent 自报或 receipt received，均不自动转移总任务责任。

新 API 拟定为 `GET /api/v1/command-center/tasks`，默认 20 项、最大 100 项。详情沿用任务与控制平面入口；新增写操作放在指挥台专用路由，具体请求 schema 在 CMD-01 冻结。全部使用现有 loopback、token、Host/Origin 保护。

列表按固定排序键和 ID 稳定分页；游标绑定过滤条件与投影 generation，变化时显式要求刷新。责任/健康度等过滤先基于完整、有效投影选择结果，再分页，不能只过滤当前页。响应包含生成时间、投影覆盖水位和缺口说明。

缓存由原始事实重建。新事件、receipt/attestation、authority、任务关联、人工更新、来源撤销和审查结论都必须触发正确失效；重建中提供明确状态，不能返回假“无任务”。汇总读取在一致视图中完成，避免把旧 manifest 和新 receipt 拼成已确认交接。

默认只对仍被观察为 running/waiting 的运行，在 60 秒没有新观测时提示“超过观察窗口”，并展示阈值和最后时间；这不推导已停止。刷新周期先沿用 15 秒，页面不可见时降低无用请求，销毁时取消请求。缺失/异常时间显示未知，不用扫描时间伪造源动作时间。

CMD-04 的新写操作使用服务端签发的状态标记绑定 task revision 与控制水位，事务内检查并更新。重复同一请求保持幂等，内容冲突返回明确冲突；不接受客户端自填的 authority。旧 API 的兼容策略必须在交付卡写清，不把新增必填字段直接塞入旧请求。

CMD-05 的 review 是独立审查记录，不能塞进 decision/constraint 文本或普通来源事件来获取权限。用户确认由明确的受保护操作写入，Agent 或导入的“通过”只作未验证观察。现有 `appendAuthorizedEvents` 的类型白名单不会为任意 review JSON 放宽。人工批准也不自动创建 receipt attestation、启动目标或改变任务完成状态。

### 6.3 G2 功能与故障验收

- [ ] **CMD-AC01 · 30 秒定位**：准备含执行、待输入、缺回执、待审、请求修改、未知和冲突的至少 12 个任务。测试者在 30 秒内找到指定的待处理任务、责任方和证据入口。
- [ ] **CMD-AC02 · 修复—审查闭环**：分配执行者和审查者，提交 snapshot A 待审，记录请求修改，再产生 snapshot B。A 的结论保留；B 不继承批准，重新审查后才有 B 的有效结论。
- [ ] **CMD-AC03 · 信任隔离**：导入伪造 user/runtime 来源、已确认责任、已批准审查、verified-complete、已有证明 ID 的 JSON，均不能获取新增 authority、有效批准或 receipt 确认。
- [ ] **CMD-AC04 · 多运行隔离**：同 session 两个 run、同名任务、不同项目/工作树、延迟/乱序/重复事件不串状态；缺少身份字段时保持缺口。子任务创建不转移总责任。
- [ ] **CMD-AC05 · 责任冲突**：同 scope 出现多个未结束的已确认执行者时展示冲突和证据，不任意选“最新一位”掩盖问题。用户显式解决，历史保留。
- [ ] **CMD-AC06 · 并发更新**：两个标签页同时改分工或审查，旧状态提交被拒绝；输入草稿保留，可比较后重试。过滤/分页变化不把旧选中对象的操作提交给新对象。
- [ ] **CMD-AC07 · 回执与版本**：错误目标、过期 revision、错误摘要、旧 stage、nonce 重用、缺少 attestation 和来源消失均显示准确状态。点击详情与列表一致。
- [ ] **CMD-AC08 · 失败及恢复**：局部查询失败、断线、重启/换端口、来源撤销、投影重建、时间缺失/偏差和坏历史记录均有可操作提示；人工任务、角色、审查历史和草稿按各自协议保留。
- [ ] **CMD-AC09 · 操作边界**：准备接续进入现有完整预览与终端确认流程；没有控制能力时显示能力缺口。普通刷新与证据下钻不发送消息、启动或停止 Agent。
- [ ] **CMD-AC10 · 可访问性与隐私**：键盘可操作，状态有文字，1280×800 与 768 px 宽度可用；DOM、响应、导出与错误消息不泄漏测试凭据和私人来源路径。
- [ ] **CMD-AC11 · 持久化**：重启后职责与审查结论可追溯；清空派生缓存再重建得到相同事实，历史 source 自报仍不能变为有效授权。

### 6.4 性能、迁移与 G2 出口

指挥台新增专用合成数据集，目标为 500 tasks、2,000 sessions、50,000 control events，包含 manifest、receipt、authority 与审查记录。该数据集补充现有 benchmark，不替换原有搜索基线。

- 100 次预定义混合过滤/分页请求，API p95 ≤ 300 ms，浏览器可见结果 p95 ≤ 500 ms；索引或投影更新同时发生时也测量，并保留独立分组结果。
- 服务 RSS 峰值 ≤ 400 MiB，已有 status p95 ≤ 200 ms；测试机、预热、样本数与测量范围写入结果。
- 页大小从 20 增至 100 时 SQL 往返数量保持常数级。记录查询数、扫描/重放范围，不能靠跳过行或忽略缺口达到延迟目标。
- 长重建可取消并可恢复，游标和批次原子保存；更新序号不要求连续，相关事件变化不会留下永久旧缓存。

CMD-02 和 CMD-05 如引入迁移，分别使用实施当时的下一个空闲编号，不能预先把“16/17”写死。升级必须保留 schema 15 的 authority、receipt attestations、草稿身份以及任务/决定修订；缓存可以重建，人工分工与审查记录属于需保留的用户数据。

**G2-T 技术验收**：全部 CMD-AC、性能与迁移回归通过；实现没有扩大导入事件的权限；最终候选所声明支持的接续矩阵通过；最终 head 的完整自动验证和三平台 CI 成功。

**G2-U 使用验证**：邀请 5 名外部开发者做任务试用，至少 4 人无需代操作在 5 分钟内找到自己的任务并准备接续，至少 3 人完成一次真实接续；另记录指挥台 30 秒定位任务。外部参与者可以在 G2-T 后招募；缺参与者时该门槛保持待完成，后续独立工程工作可按 G2-T 推进，对外使用验证与相应发布声明仍受 G2-U 约束。开发代理实测不能充作外部参与者。

## 9. 迁移、回退与持续约束

- 阶段 1 默认不改数据库。确需持久化新的认证元数据时，先说明离线可重建文件是否足够，再决定迁移；不能以“认证”名义重写旧 receipt 或 authority。
- 每个有迁移的包，以真实 schema 11、14、15 库及包含人工任务、修订、manifest、attestation、草稿身份和坏历史事件的 fixture 升级；覆盖 WAL 已提交数据、失败回滚和幂等重开。
- 比较升级前后人工业务数据和信任状态。旧自报可以作为观察保留，不能被新投影、审查或采集逻辑升格；有效证明和数据库身份不能丢失。
- 升级前备份包含 WAL 中已提交内容；备份失败不开始迁移，DDL/版本更新按现有事务规则。旧版本拒绝新库是预期行为。
- 新增只读工作区和变化审阅路径复用经过审查的 reader 与预算，不重新引入会运行仓库 filter、外部 diff、fsmonitor 或不可信 PATH 程序的读取方式；必要新增 Git 调用单独复审执行边界。
- 普通代码回退使用实际 squash SHA 的 revert PR，并先检查下游。数据库回退优先前向修复；确需恢复时停用相关服务、保留现库，在新目录恢复兼容备份，核对备份后人工编辑损失后另行决策。不能降低 `user_version` 冒充兼容。
- Capsule v1、handoff v1 与旧 CLI 输出继续兼容。新增契约使用独立版本/入口；受限 Git 场景、raw 字节语义及跨 dataDir 协调限制继续明确显示。
