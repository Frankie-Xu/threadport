## 2. 首版的明确选择

- 形态：npm 分发的本地 CLI + 浏览器工作台；一个仓库、一个 npm 包，无账户、无托管服务。
- 首版新工作台认证目标：macOS arm64、Ubuntu x64，Node 24。Windows 保留旧 CLI 回归，新工作台只在实际验证后声明支持。
- T05 已将开发分支运行时门槛提升到 Node `>=24.0.0`，见 [运行时与存储迁移](07-storage-migration.md)；现有已发布版本不受追溯改变。
- Claude Code、Codex CLI 的本地日志发现和真实接续为必交付；Cursor/Gemini 保留已有手动解析能力，不因为已有 parser 就声明原生接续受支持。
- 三个主要页面：任务首页、任务详情、接续预览；提供简洁设置页用于来源、存储和诊断。
- 浏览器负责准备接续。用户复制固定格式的 ThreadPort 命令，在终端确认后启动目的端 Agent。首版不内嵌终端，不承诺浏览器一键打开所有系统终端。
- 核心不修改源代码、源会话和 Git 历史；启动目的端后，目的端按自己的权限工作。预览与终端确认清楚说明这一边界。
- Capsule v1 继续兼容。任务、证据、校验报告存在内部模型及独立版本的接续包中，不把新字段偷偷塞进旧协议。

## 3. 新旧规则的衔接

`docs/DEV-PLAYBOOK.md` 记录的是 0.1 阶段，包含已经完成的适配器任务、旧测试数量和旧机器路径。**v0.2 的产品范围、顺序和验收以本目录为准**；旧手册保留历史价值。

现有 CONTRIBUTING 的“不自动执行 next_action”“不上传原始会话”“不修改 Capsule v1”继续有效。本计划开放的是用户主动确认的目的端启动，执行器不得把日志中的命令或 next_action 当作 shell 代码。T01/T19 会把这些变化同步到贡献指南和用户文档，避免新旧入口互相矛盾。

执行时如果 HEAD 变化，先记录新 SHA、重跑基线、核实本计划提到的问题是否仍存在；已经合并的修复只补缺失验证，不重复实现。不得清理其他任务已有的未提交文件。

## 4. 完成度采用证据，不采用百分比

| 等级 | 定义 | 可以对外怎么说 |
| --- | --- | --- |
| L0 设计 | 边界、契约、验收写清 | 计划支持 |
| L1 实现 | 代码可运行，关键单元测试通过 | 开发中 |
| L2 集成 | 合成数据端到端与失败分支通过 | alpha / 实验性 |
| L3 实机 | 发布产物、声明平台及真实 Agent 版本通过 | 支持指定版本与平台 |
| L4 使用验证 | 外部用户独立完成核心流程并回访 | 已有使用证据；仍不等于 PMF |

v0.2 stable 的全部必交功能至少 L3，整体核心流程至少 L4；历史搜索等无 Agent 调用功能的 L3 是安装后在实际文件系统完成流程。未开始的功能统一记 L0，不能把“接口已定义”记为 80% 完成。

## 5. 范围变更规则

遇到新需求，先写真实用户场景，再判断是否影响「找到 → 理解 → 接续」闭环。新增必交项必须同时说明移除什么、增加多少工作和哪些验收会变；记录在 Issue 与 ADR 中。没有用户证据时，默认进入后续版本候选。

这是一套工程规格和可审查任务计划，不预写整套生产代码。接口示例是约束；实现者需要在对应小 PR 中提交实际实现、行为测试和运行证据。实施不依赖专有 Agent 插件或外部规划技能。
