# 发布与用户验证

## 1. 版本阶段

已有 0.1.0 是协议/CLI 原型。v0.2 alpha 必须已经有一条可工作的纵向流程；不发布只有空界面的工作台。产品 semver、Capsule schema version、task-handoff protocol、SQLite user_version、source parserVersion 独立管理。

| 阶段 | 功能门槛 | 可以招募谁 | 不可以承诺 |
| --- | --- | --- | --- |
| 0.2.0-alpha.N | P0–P3：找到→任务→验证→至少一条真实接续，L2 为主 | 5–10 位愿意提供详细反馈的使用者 | 所有平台/所有 Agent 支持 |
| 0.2.0-beta.N | P4：完整 UI、四条路径实机、包安装、主要失败恢复 | 15–30 位目标用户 | 零丢失迁移、任意日志格式兼容 |
| 0.2.0-rc.N | 全必交项 L3，P0/P1 清零 | 独立安装验收者 | 还未验证的质量/性能数字 |
| 0.2.0 | RC 门槛 + 核心流程 L4 | 面向公开 GitHub 用户 | 10k Stars 的确定时间表 |

## 2. 支持矩阵与版本证据

维护 `docs/compatibility.md`：每行必须包含 source tool version、target tool version、OS/arch、Node patch、mode、验证日期、ThreadPort SHA、结果与限制。未测标 unverified，禁止留空让读者误解。

必测目标：macOS arm64 + Node24、Ubuntu x64 + Node24。每个平台分别测 Claude→Claude、Codex→Codex、Claude→Codex、Codex→Claude。同 Agent 的原生恢复确实不可用时说明 new-session 降级，并相应收窄 F08 的支持声明；stable 要么实现原生恢复门槛，要么经明确范围变更后发布，不可偷偷用降级代替。

Windows：已有 extract/validate/render/handoff/targets 在 Windows runner 回归；新 UI 可开 experimental，但未完成 F01–F10 安装/实际接续认证前不写完整支持。Cursor/Gemini 明确 parser-only。未知新版 Agent 优先降级到导出，保留日志发现的 partial 标记。

## 3. 真实接续验证方法

使用隔离、人工构造的小项目，预设三个任务：修复一个带测试的函数、遵守“不修改指定文件”的约束、在最后一次测试失败的位置继续排错。为每个方向至少跑三种任务，成功标准不是回答“我理解了”，而是选对目录、复述/遵守人工约束、完成预设下一步，并由测试或人工检查确认。

同一任务进行两个对照：仅仓库 + 人工简短 HANDOFF.md，以及 ThreadPort。记录准备时间、接续前补问次数、重复探索、约束漏失、任务是否完成。样本很小，只用于定位产品问题，不发布“提升 X%”的总体结论。

目的端 Agent 费用由维护者承担；使用测试账户和无秘密临时项目。记录模型/工具版本与权限模式，不能用一端自动批准、另一端手动逐项批准来制造优势。复测失败必须保留，不只挑好看的演示。

## 4. 安装与分发门槛

发布目标是用户无需克隆源码。选择可用且由维护者控制的 npm 包名，T19 核实注册表状态、所有权和凭证；若无 scope 名不可用，使用已拥有的 scope 并统一 README，不杜撰安装命令已经可用。

每个 RC 用 `npm pack --json` 得到 tarball，临时空目录安装它，并验证：

- `threadport --help` 及所有旧命令；UI 静态 assets 随包，运行时不依赖源码目录。
- better-sqlite3 在目标平台/Node24 干净安装，失败信息可定位。
- 包只含 dist、schema、examples、必要 UI assets、许可证/README；不含 tests、research、私人 HTML、源日志或本地 DB。
- 库 import 无副作用，types 可解析；CLI executable 权限正确。
- 初次运行、重启、升级、迁移失败恢复、离线 UI 可用。

先产出带 SHA-256 的 RC 包和验证摘要，再创建 Release。发布用受控 CI/维护者流程，具体凭证方案以账户可用能力配置；不把 token 写入仓库。Tag 对应实际验证 SHA，Release Notes 包含支持范围、变化、升级/回退和已知限制。

回退：服务停止，安装前一兼容包，必要时恢复升级前 SQLite backup；若旧版不识别新 schema，则拒绝打开，不能拿旧二进制直接碰新库。发布错误先停止推广，修复版本，不通过改 Git tag 隐藏问题。

## 5. 面向 Stars 的首发包装

一句话定位候选：**Find your unfinished AI coding tasks. Continue with Claude or Codex.**

README 首屏只放用户结果、真实 30–45 秒演示、已核实安装命令和三步 quickstart。技术协议解释放后面。演示顺序：搜索昨天的任务 → 看到最后失败/人工约束 → 选择另一个 Agent → 预览 → 终端启动继续。终端确认真实呈现，不剪辑成产品做不到的一键能力。

准备三个可复制素材：

1. 找回旧任务：面向所有 Claude/Codex 使用者，强调不用手工找日志。
2. 换 Agent 接续：面向双工具用户，强调具体流程与限制。
3. 昨天通过、今天不一定有效：演示 stale/unknown 处理，解释可靠性价值。

仓库展示可读 task Markdown 样例，用户不安装也能理解产物。提供 demo 模式，让没有本地日志的人体验；demo 不是用户激活。Star 提示只在 README 和 About 放轻量链接，不要求 star 解锁、不购买 stars、不自动替用户点星。

## 6. 发布渠道与节奏

alpha 优先邀请有多个会话/项目的独立开发者，观察实际操作。beta 把安装痛点处理完再在相关 CLI 社区、个人技术博客和 GitHub Discussions 分享工作实例；遵守社区自荐规则。stable 再考虑 Show HN、开发者社区和演示视频，使用真实结果与竞品差异，不刷多个同质帖子。

每次传播只验证一个主张：找得回、接得上、状态清楚。竞争对照以已测具体版本/功能为准，给竞品链接和适用场景，不宣称“所有其他工具都不支持”。

为外部贡献准备 3–5 个真正可独立完成的小 Issue，例如某日志版本 synthetic fixture、Windows 路径边界、搜索 UX、英文说明。生态传播来自可参与的工作，不能只在 README 写 welcome contributions。

## 7. 指标与决策

默认无遥测。alpha/beta 用用户同意的操作观察、人工回访和用户主动导出的本地计数；公开仓库 Stars/traffic 由维护者在有权限时查看。没有对应权限/数据时写 unknown，不用 npm 下载量充当活跃用户数。

| 指标 | 精确定义 | 如何采集/如何判断 |
| --- | --- | --- |
| 安装成功率 | 成功打开真实工作台人数 / 尝试安装人数 | 观察样本，记录版本和失败；demo 单独计 |
| 首次激活 | 找到自己的会话，并创建/关联一个任务 | 用户同意的观察或本地计数，不计 demo |
| 接续尝试 | 完成确认并实际启动目标 Agent | launch attempt，仅本地记录 |
| 接续成功 | 用户确认正确接续 + 预设下一步证据 | 人工确认；不以 exit 0 推断 |
| 次周回访 | 激活用户中第 7–13 天再次操作真实任务者比例 | 小样本人数与比例同时报告 |
| Stars | GitHub 累积/净增 stars | 分发指标，无法直接归因于某次产品操作 |
| 外部贡献 | 有独立贡献者完成的有价值 PR/兼容验证 | 不计维护者自开 PR 和机器人依赖 PR |

stable 可用性门：5 名外部用户中至少 4 人 5 分钟内独立找到会话并准备接续，至少 3 人完成实际接续。增长方向门另行观察 beta 激活者至少 15 人，其中至少 5 人在下一周回来使用真实任务；这是探索阈值，不是统计显著性或 PMF 标准，未达到不应隐瞒。

如果大家只看演示不安装，优先检查定位和安装；安装但不激活，修发现/搜索；激活不再来，验证任务收件箱是否有日常价值；反复用但不分享，改善可读导出、演示和协作入口。不要用增加第五个 Agent 来回避核心留存问题。

## 8. 首版之后的候选

按真实需求选择其一：提高任务自动关联准确度、Windows 完整认证、第三种 Agent、分享给另一个人的本地任务包、原生桌面入口。云同步、收费团队协作和多 Agent 方案对照需要额外规格，不能以“首版顺手加”进入本次发布。
