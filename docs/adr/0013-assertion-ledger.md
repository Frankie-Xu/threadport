# ADR 0013: Immutable decisions, explicit replacement and conflicts

Date: 2026-09-16. Report item R05. Database schema 6.

Assertions are separate from the original task's manual objective/constraints/next action. Each entry records decision or constraint, explicit topic, task/workspace/relative-path scope, provenance, confirmation/lifecycle, applicability, replacement edges and immutable revisions. Both a ledger revision and a task revision are written in one immediate transaction, so every mutation invalidates old previews and stale editors. Source indexing does not write this table.

New entries are candidates by default. Confirmation is an explicit user action, including when the text originated in an assistant event. Candidates cannot replace anything. Replacement creates a new ID and can supersede only active entries in the same task, topic, kind and exact scope; retired IDs cannot revive. Edges point only from newly generated IDs to existing IDs, making cycles unrepresentable. No latest-timestamp rule decides authority. Existing task constraints remain in force independently.

Different confirmed texts sharing a topic/kind and overlapping scope are disputed; the user can also explicitly mark any two overlapping confirmed entries as conflicting across topics or kinds. This is a conservative explicit model, not language-level contradiction detection. Topic comparison is case-sensitive. Explicit rejection or replacement resolves a dispute; history remains. Confirmed entries with unknown applicability and unresolved disputes in the selected workspace block handoff preparation with ASSERTION_CONFLICT. A path scope is included in the transmitted statement; workspace-scoped entries are included only for that workspace.

The compiler emits effective confirmed decisions into existing Capsule v1 decisions and appends effective ledger constraints. Candidates remain separately labeled unconfirmed prompt metadata. Superseded entries are not current decisions. Required assertion content is never silently truncated to meet the 32 KiB prompt budget; an over-budget handoff is refused. Candidate text can be shortened or rejected through an explicit revision workflow before retrying.

Source references preserve the session/event IDs and a digest of the normalized event observed when the entry was created. The UI reports unavailable if the event changed/disappeared, the session detached, the source was revoked, or its path is not readable. Otherwise it says indexed-only: filesystem accessibility and cached event identity do not reparse or authenticate the current raw source. User confirmation survives missing evidence; no historical evidence is invented.

API mutation bodies are strict and authenticated through the existing loopback boundary. Credentials require redaction review. Display/export text crosses the portable redaction boundary. The editor retains a draft after a revision conflict; an explicit baseline refresh keeps the draft and requires another save. A confirmation checkbox and replacement checklist make adoption distinct from drafting. Entries can also be drafted directly from the evidence viewer.

Bounds: 200 distinct entries per task, at most 2,000 existing history rows before a write (a single replacement can append up to 201 rows). History is retained across cache rebuild/revocation and normal handoff retention; explicit deletion of all application data still removes the database. Migration 006 adds the ledger without rewriting task fields; updates to stored revision rows are rejected. Older schema-5 binaries refuse schema 6. Prefer a forward fix; restoring a pre-upgrade backup does not retain subsequent user edits.

Acceptance covers explicit A→B, candidates, assistant provenance, conflicts across topics, scope/task validation, unrepresentable reverse edges, stale revisions, source/cache loss, compiler blocking and browser draft recovery. These are synthetic development checks and do not replace the real Agent matrix, external-user observations or original 36-scenario specifications.
