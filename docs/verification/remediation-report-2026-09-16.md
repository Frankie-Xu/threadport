## 1. 结论与整改目标

项目已有可运行的本地工作台：日志索引、历史搜索、任务编辑、工作区检查、交接预览、终端确认和本地数据管理均有实现。被评估任务完成了首批证据适用性改进，未完成整份开发报告要求。

当前适合在已知边界内开展开发验证，稳定发布继续保持 **HOLD**。主要差距是：历史证据采集尚未闭环；决策替代与冲突模型缺失；启动授权、工作区并发和崩溃恢复需要加固；部分工作区场景与敏感文件策略未覆盖；真实双 Agent、性能和用户验证尚未达到门槛。

整改目标是形成可追溯、可验证的任务接续闭环：确认有效决定 → 核对工作区 → 正确标注历史证据 → 审阅确切交出内容与启动计划 → 单次授权启动 → 记录实际结果和不确定状态。自动化检查通过只是其中一层证据。

本报告只新增整改文档，未修复业务代码、变更支持范围或执行发布。以下新增方案均为待实施；原有能力与已完成改动另行列明。

## 4. 修复方案与验收标准

### R01｜固化首批交付

**现状：** 当前 HEAD 不包含新增证据模块等改动；工作区同时存在与本包无关的文件。只记录 HEAD 无法重现本轮测试对象。

**整改：** 按文件归属整理首批增量，保留已有无关修改；为本工作包记录基准/最终提交、变更清单、验证环境及回滚依赖。按仓库流程由维护者审阅、提交，再进入 PR。补跑 Node 24 与安装后的工作台验证。

**验收：** 独立检出该提交即可复现检查；`npm run check`、相关浏览器流程与 `npm run test:package` 通过；产物记录提交 SHA、tarball SHA-256、OS/Node 和工作树状态。不得将当前未提交改动归入旧提交的认证结果。

### R02｜将审批绑定到最终启动计划

**源码依据：** [启动流程](../../src/targets/launch.ts) 在终端确认后调用 `runner.prepare`；[记录摘要](../../src/storage/handoff-store.ts) 绑定交接记录，未包含完整最终 `LaunchSpec`。现有流程已检查原样上下文、工作目录、任务和工作区变化，应保留。

**整改：** 先构建并冻结启动计划，再供终端审阅。绑定目标工具、规范可执行路径及可复核身份、版本、argv、cwd、传输方式与内容摘要、可控制的权限选项、有效期和单次 nonce。对继承但不可观测的 Agent 配置明确显示边界，不宣称已完全锁定外部权限。启动前重验身份、绑定字段和工作区；任何不一致要求重新准备和确认。

**验收：** 确认期间切换 PATH、替换目标程序、改变参数/传输方式/目录/权限选项时拒绝原授权；完全一致只允许一次消费；无 TTY、取消及过期不启动；保留 `shell:false` 和原样上下文检查。需记录可执行文件复核与实际启动之间仍存在的系统级竞争边界。

### R03｜增加工作区互斥和不确定运行态

**源码依据：** [启动存储](../../src/storage/launch-store.ts) 以 handoff ID 认领，观察者身份主要依赖 PID；丢失观察者记为 `interrupted/OWNER_LOST`，并不证明目标 Agent 已退出。

**整改：** 为同一规范工作树建立跨进程、跨交接包的认领机制，明确多数据目录是否共享协调及其支持边界。记录 run nonce、观察者/目标进程身份，以及平台能够可靠取得的启动时间和启动会话标识。无法确认目标是否存在时进入明确的 unknown 状态，保留占用或要求显式恢复；不得以超时或 PID 不存在直接推导可安全重启。只协调 ThreadPort 发起的运行，不宣称锁住所有外部编辑器和 Agent。

**验收：** 两个不同包竞争同一工作树最多一个被启动；独立 worktree 可分别执行；在认领后、spawn 前后、回执前注入崩溃均不自动重试；模拟 PID 复用不会错误释放占用或终止其他进程；人工恢复有可审阅证据和记录。

### R04｜补齐工作区读取边界与覆盖说明

**源码依据：** [工作区读取器](../../src/workspace/reader.ts) 枚举 tracked 和未忽略的 untracked 文件并读取内容，没有独立敏感文件排除规则；未被 Git 忽略的 `.env` 可能进入指纹读取。symlink、submodule、无提交仓库和非 UTF-8 路径存在保守拒绝。拒绝策略不等于已支持这些场景。

**整改：** 引入版本化范围策略，默认不读取敏感文件内容，明确其遗漏及对验证结论的影响。Git 忽略规则不能作为唯一隐私策略。符号链接只检查链接文本和越界关系；子模块、ignored 文件、超预算和无法读取项须分别解释。对无提交仓库和字节路径选择实现或明确受限支持，禁止静默跳过后仍标“完整”。

**验收：** 用合成敏感文件证明未进行内容读取，而不只是输出中找不到秘密；tracked `.env` 也被处理；越界链接不读取目标；遗漏、预算和特殊路径结果可见；检查失败时不生成可启动的虚假完整快照。指纹或范围算法变化须版本化，旧快照不得直接按新算法视为匹配。

### R05｜完成决定修订、冲突与交接编译

**现状：** 已有任务人工字段、乐观修订和重扫保护，但缺独立 assertion 模型及明确替代链。新增代码不能用简单“最后一句优先”代替决策治理。

**整改：** 在现有任务修订旁新增可追溯条目及不可覆盖修订，分别记录类型、来源/确认、生命周期、适用性和作用域。替代关系须同任务、无环且明确；冲突不能靠时间排序自动解决。将生效条目、候选和争议接入编译器及工作台，规定未解决的关键争议如何阻止生成可执行交接。保持既有 Capsule v1 公共契约兼容，内部模型单独版本化。

**验收：** “A 被明确替换为 B”只将 B 作为当前决定；“也许 B”保持候选；assistant 建议不能撤销已确认约束；两条冲突人工决定必须可见并显式解决；跨任务替代和环被拒；重索引不覆盖人工修订；并发保存冲突保留草稿；源引用不可重读时显示不可用。

### R06｜打通命令、快照与环境证据链

**源码依据：** [来源归一化](../../src/sources/claude-events.ts) 中命令的 `snapshotId` 为 null，Codex 来源复用该归一化路径；[判断器](../../src/evidence/command.ts) 有意只输出 unverified、stale、unknown，不输出 current。

**整改：** 为可观测的新执行定义证据生产协议，记录真实 argv/cwd、开始结束时间、退出状态、执行前后快照、明确的环境范围和可取得的测试数量。接入方式先写 ADR；若支持主动运行检查，须与只读比较分开，由用户明确触发。不得重建或伪造旧日志不存在的历史现场，不从 shell 文本猜出结构化 argv。

**验收：** 在同一受控场景完成“执行记录 → 保存快照/环境 → 后续代码变化 → prepare 显示 stale”；无历史绑定仍 unknown；不完整结果仍 unverified；null 数量不变成 0；执行期间现场变化不得标 current。只有代码、环境及声明范围均有充分证据时才可引入范围受限的 current。所有历史警告继续覆盖被省略的片段。

### R07｜修复脱敏后的可操作性并验证目标传输

**历史依据：** [真实 Codex 记录](real-codex-macos.json) 第一场景中，绝对 Node 路径脱敏为 `external/...` 后首次执行 exit 127，Agent 改用 `node` 后才完成。后续成功不能消除该首次失败记录。

**整改：** 区分“供审阅的历史命令”和“用户确认的下一步操作”。被脱敏或丢失执行路径的信息必须标为不可直接执行；需要可移植命令时由用户确认或经确定性、已验证的映射生成，不能靠恢复私有路径或 Agent 猜测修复。对完整上下文经 argv 传递的隐私、长度和兼容边界进行评审；仅在目标确实支持并实测后采用 stdin、受限临时文件或其他传输方案，不预设 vendor 能力。

**验收：** 原失败场景有可复现回归；交接不会把脱敏占位符呈现为已验证可执行命令；保护约束和文件不变；真实目标收到的内容与批准摘要一致。验证大文本、Unicode、引号、换行、临时文件清理和失败恢复；不支持的传输明确降级为导出。

### R08｜按固定容量修复搜索延迟

**历史依据：** [性能记录](performance-beta.md) 基线搜索 API p95 为 375.12ms；后续独立轮次为 910.60ms。浏览器复测所在轮次 API p95 为 456.14ms、可见延迟 p95 为 593.70ms。不同轮次不合并，均不能证明达标；当时主机存在其他负载。

**整改：** 先在固定参考环境建立可重现样本，区分数据库查询、数据读取/投影、响应和页面呈现耗时，再选择优化。保留中文子串、字面 `%/_/反斜杠`、NUL 后文本、稳定分页和过滤语义。不能以缩小样本、减少查询种类或放宽原门槛宣称修复。

**验收：** 在 200 MiB、500 会话、50,000 事件、100 次混合查询条件下，API p95 ≤300ms、UI p95 ≤500ms；索引、内存、启动和取消仍满足原预算。保存全部样本、机器负载、版本和失败轮次，分别记录 macOS/Ubuntu 结果。当前报告没有完成该性能复测。

### R09｜补齐真实验收与发布证据

**现状：** [Agent 矩阵](agent-matrix-beta.md) 已运行 3/24 格，均为旧安装包的 macOS Codex→Codex 场景：2 格 observed_pass、1 格 observed_with_issue；21 格未运行。[外部用户记录](user-study-v0.2.md) 为 0 名已观察用户。输入报告提到的 36 场景附件未纳入本次评估，不能以现有 Q01–Q24 或 395 项测试代替逐项验收。

**整改：** 收集并版本化 36 场景原始规格，建立“要求 → 代码/测试 → 运行证据 → 缺口”表；未取得的条目保持未评估。按现有承诺完成两个平台、四条来源/目标路径、三个任务的矩阵，并针对实际支持的 native-resume/new-session 模式补充验证。所有真实测试绑定最终候选提交、安装包摘要、OS/Node/CLI 版本。

**验收：** 每格核对目录、完整人工约束、目标产物和独立结果，不能只看 exit 0；保留首次失败和重测记录。按既有用户门槛观察至少 5 名外部用户，其中至少 4/5 在 5 分钟内独立准备接续、至少 3/5 完成实际接续；记录许可与卡点，不收集私人原始日志。最终 RC 重新通过源码、浏览器和安装包检查。若调整支持范围，须同步需求、文档和门禁，不得静默把未测格改成通过。

### R10｜统一文档状态和证据版本

**现状：** [文档入口](../README.md) 仍保留“当前 0.1.0 未实现任务工作台或原生接续”的旧表述；[质量门禁文档](../v0.2/04-quality-gates.md) 有早期未来时描述；部分交接和发布摘要未纳入最新性能复测。单个文档存在记录，不等于各入口状态一致。

阶段之间可以预先准备 fixtures、测量和文档，但最终认证必须使用包含上游修复的候选包。R05、R06 等较大项目应拆为多个可独立审阅的小 PR，避免一个大改动同时重构存储、启动与 UI。

每个工作包必须包含：问题复现或已确认的需求差距、契约/ADR、受影响文件、关键失败路径、回归证据、兼容性、回滚及剩余限制。涉及存储时使用增量迁移，不能用报告中的新库 DDL 覆盖当前 schema v4；验证迁移失败恢复，明确旧版本是否还能读取新数据。回滚代码不能被描述为恢复已删除用户数据。

## 6. 发布解除条件

维持现有 HOLD，直至以下条件逐项有证据：

- 首批及后续改动有可重现版本，最终候选在 Node 24 和声明的平台通过所需检查。
- 核心授权、工作区隔离、敏感文件读取、决策冲突和历史证据场景达到本报告验收要求；未解决的 P0/P1 不进入 stable。
- 36 场景原始规格已取得并逐项核验；现有 Q01–Q24 门禁也有当前证据，不能互相代替。
- 真实平台/Agent 认证覆盖发布声明，性能达到既有门槛，外部用户试用达到既有标准。
- 最终安装产物、迁移/恢复、兼容限制和文档相互一致；记录审查者身份，代理自审不冒充外部独立评审。
- 维护者作出明确发布决定；测试通过本身不构成发布授权。

本报告提出的首个执行动作是 **R01：固化已验证增量及其证据**。随后优先完成 R02–R04，避免在扩大真实接续使用前继续累积启动和工作区边界缺口。
